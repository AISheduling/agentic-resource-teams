# Scope of the problem-solving solution

Each reviewed work solves one part of the task:

- LMDX attaches every extracted value to a line on the page and discards values not found there, but only for form fields; its 16 samples per chunk are merged by voting into one result.
- ConstraintLLM and OptiMUS check the result by running it in a solver, but they start from a text that describes the problem, not from documents about resources. Lappas et al. treat skill coverage as a hard condition, but build skills and the graph from a bibliographic database.
- RAG, ReAct and Adaptive-RAG search for sources and answer, but return one answer and do not tie it to the supporting fragment, moreover for Adaptive-RAG this is based on the abstract only.
- López-Pintado and Dumas build a resource model, but from event logs, not from documents, and return one model.
- Brinkmann et al. extract attribute-value pairs and normalise them; values are checked to be substrings of the text only when the gold standard is built, and the model output is not checked against the source.

None of the ten works combines all of the following in one method:

- extracting parameter from heterogeneous documents;
- linking each value to a fragment of the source;
- telling a mandatory norm from an example;
- checking the assembled team with formal constraints;
- returning several admissible options to the user;
- showing conflicts between sources instead of choosing or averaging silently.

Items 3 and 6 are not shown in any of the ten works. The other items occur only separately, and item 1 only partly at López-Pintado and Dumas from event logs and Brinkmann et al. from product text.

# Importance for resource team

If the system fills the gaps itself, the plan receives requirements that look reasonable but nobody confirmed: an invented qualification, a crew size taken from the wrong card, a norm from the wrong edition. Real documents also disagree with each other, so a silent choice of one value can change the planned labour and duration considerably. And for some jobs the sources contain no data at all, and the only correct answer is «not in the sources». So a system is needed that not only finds values but shows where each one comes from, how it was confirmed, which sources conflict, and what could not be confirmed.


# Hypothesis

On the same set of sources and with the same budget, an agent loop (propose a candidate team, look for confirmation of each requirement in the sources, check with formal constraints, correct) gives a share of fully suitable teams that is at least 10 percentage points higher than the better of two simple methods, and its share of unconfirmed mandatory requirements is not higher than that of ordinary RAG. The gain is expected to be larger on inputs with gaps and with different terminology than on full inputs.

# Compared methods
- Rules and the nearest template from the norms, without an LLM;
- Nearest norm template: take the closest norm or typical card for the job and copy its crew and norms, without an LLM;
- Ordinary RAG: one search over the corpus and one answer;
- Agent loop: the model proposes candidate modes from the sources and from its own knowledge, marks the part that comes only from its own knowledge as a hypothesis, looks up confirmation for each requirement in the sources, checks the mode with formal constraints and corrects it, repeating within the budget.

# Equal conditions

- all methods use the same registry of documents and nothing else;
- the same jobs, each in three forms of input: full, short (with gaps), and with different wording;
- the same cap per job on the number of model calls and tokens, including search and checking. The cap is fixed before the first run. Real cost is recorded separately and does not count as success;
- the same program checker and the same expert, who does not know which method produced the answer. The checking rules and the expert protocol are recorded in the comparison plan before the first experiment.

# Metrics.

Share of fully suitable teams = variants where the team passes the checker and the expert accepts it, divided by all variants. A refusal or «unknown» counts as not suitable.
Share of unconfirmed mandatory requirements = mandatory requirements in the answers that have no source reference or are refuted by a source, divided by all mandatory requirements in the answers.
Both are reported for all variants and separately for each form of input and for each job.

The hypothesis is not confirmed if at least one of these holds.

1) The share of fully suitable teams of the agent exceeds the better simple method by less than 10 percentage points over all variants (the threshold is a starting one and is revised after the pilot).
2) The share of unconfirmed mandatory requirements of the agent is higher than that of ordinary RAG.
3) When the budgets are equal the gain disappears, that is, the agent wins only when it is allowed more calls.
4) The agent's gain on short and reworded inputs is not larger than on full inputs; then the part of the hypothesis about gaps and terminology is not confirmed, the rest is assessed separately.
5) On a job that has no answer in the corpus the agent returns a team instead of «no data», or on a job with conflicting sources it silently takes one value or averages.

# Limits of the check.

On 7–10 jobs one job weighs 10–14 percentage points, on 21–30 variants one variant weighs 3–5, so the 10 points are a working threshold, not a proof. Results are given per job, and the way to assess significance (paired comparison by variant) is agreed with the supervisor.

# The axes

- What is extracted and where from. Our output is a resource mode (roles, qualifications, number of people, equipment, norms), and the input is heterogeneous documents. These axes show whether a work solves this task or a neighbouring one (answers to questions, product attributes, event logs, a social graph).
- Distinguishes norm, example and history. In our corpus a typical card is an example, a norm is mandatory, and history is an observation. Without this axis a method can turn an example into a mandatory requirement, which is exactly what we count as an unconfirmed requirement.
- Grounding to a fragment and how the result is verified. «Grounded» in the hypothesis means a source reference for every mandatory requirement plus a formal check, so these two axes show whether a work could provide it. Verification is split into a check of one output and an evaluation of the method, because the hypothesis needs both.
- Multiple candidates and source conflicts. The goal is several admissible modes with the conflicts between sources shown, not one answer.
- Role of the LLM. It shows where the model stands in the pipeline and whether its own knowledge is used; the hypothesis compares a loop with the model's own knowledge against methods without it.
- Cost. The comparison is at a fixed budget, so cost is recorded as a measured quantity with its conditions. In the reviewed works only machine cost was recorded; the expert effort that our hypothesis also measures is not reported there, so it is measured in our experiment, not taken from the analogs.
